# 第一部分 CAN 基础

## 1. 网络拓扑

CCU（地址 0x03）是诊断主节点，MCU（地址 0x0D）是诊断目标节点。MCU 再通过 UART 转发给 Qi 芯片。

```
CCU (0x03)  ──── CAN 总线 ────  MCU (0x0D)  ──── UART ────  Qi 芯片
  诊断主节点                        诊断目标节点                Qi 充电芯片
```

多个外设可共享同一 CAN 总线，每个外设使用唯一的源地址。

## 2. 物理层参数

| 参数 | 值 |
|------|-----|
| CAN 标准 | CAN 2.0B，Classical CAN |
| 波特率 | 250 kbps |
| 帧格式 | 29-bit 扩展帧 |
| 最大 DLC | 8 字节 |
| 字节序 | 小端（Little-endian），除非另有说明 |
| CAN 收发器 | SIT1145（SPI1 控制） |

**位时序配置**：

```
APB1 = 180 MHz → CAN 时钟 18 MHz (DIV=10)
SJW=4, BTS1=54, BTS2=18
标称 250 kbps，采样点 75%
```

**SIT1145 低功耗**：Standby 时 CAN 收发器处于低功耗监听，任意 250kbps 扩展帧即可唤醒。APP 启动后恢复 Normal 模式。（当前固件 `CAN_LP_STANDBY_ENABLE=0`（can_protocol.h:63，回归调试期编译开关）：上电不进 Standby，首次 `can_protocol_poll` 统一 `enter_normal`，CAN 常在线；切换说明见 docs/14）

## 3. CAN ID 寻址

采用 J1939 风格 PDU1 寻址，CAN ID 布局：`0x18DA{TA}{SA}`

- 优先级 = 6，PF = 0xDA（点对点诊断）
- TA = 目标地址，SA = 源地址

| CAN ID | 方向 | 用途 |
|--------|------|------|
| `0x18DA0D03` | CCU → MCU | UDS 物理寻址请求（MCU 再转发给 Qi） |
| `0x18DA030D` | MCU → CCU | UDS 物理寻址响应 |
| `0x18DB33xx` | CCU → 所有外设 | 功能寻址广播（PF=0xDB，PS=0x33） |
| `0x18FF260D` | MCU → 总线 | 生命周期状态广播（APP 侧周期发送已禁用，仅事件驱动；例外：Boot safe mode 每 500ms 心跳 `01 41 42 54 cause step A5 00`） |

**功能寻址**：PS 字段为功能组地址 0x33，SA 无限制，接收端通过 PS=0x33 识别。Safe Mode 下也接收功能寻址帧。

# 第二部分 传输层 ISO-TP

## 4. 四种帧类型

ISO-TP（ISO 15765-2）负责将 UDS 报文封装到 CAN 帧中。

**Byte0 结构（重点，容易混淆）**：

> PCI（Protocol Control Information）**不是一个单独的字节**，而是和参数**挤在同一个字节 Byte0 的高 4 位和低 4 位里**。
>
> 所以当你看到 CAN 帧首字节是 `0x03`，不要以为 PCI 是 `0x03`——
> 实际上 `0x03` 拆开来看：高 4 位 = `0x0`（单帧），低 4 位 = `0x3`（数据长度 3 字节）。

```
Byte0 = [高 4 位: PCI 类型] [低 4 位: 参数]

         高 4 位           低 4 位
         0x0 = 单帧 SF      SF_DL（数据长度）
         0x1 = 首帧 FF      FF_DL 高 4 位
         0x2 = 连续帧 CF     SN（序号 0~15）
         0x3 = 流控制 FC     保留
```

**举例**：CAN 帧首字节 `0x03`，拆开来看：

```
0x03 = 0000 0011 (二进制)
       ^^^^ ^^^^
       高4位  低4位
       0x0    0x3
       单帧   长度=3
```

所以 `0x03` 同时告诉我们：这是单帧（PCI=0x0），后面跟着 3 字节 UDS 数据。

四种帧类型：

| 帧类型 | Byte0 高 4 位 | 低 4 位含义 | 用途 |
|--------|:------------:|------------|------|
| 单帧 (SF) | 0x0 | SF_DL（数据长度） | 载荷 ≤ 7 字节，单帧传输 |
| 首帧 (FF) | 0x1 | FF_DL 高 4 位 | 多帧传输的第一帧 |
| 连续帧 (CF) | 0x2 | SN（序号 0~15） | 多帧传输的后续帧 |
| 流控制帧 (FC) | 0x3 | 保留 | 接收方控制发送方节奏 |

## 5. 单帧与多帧示例

### 单帧（SF）

最常用。UDS 载荷 ≤ 7 字节时，直接放在一个 CAN 帧里：

```
CAN 数据: [PCI | SF_DL | UDS 数据 ...]
          Byte0   Byte1    Byte2~7

示例 — 读 DID 0xF195 [22 F1 95]:
  CAN: 03 22 F1 95 00 00 00 00
       ─┬─ ───────┬───────
        │          └── UDS: 3 字节
        └── PCI: SF=0, DL=3
```

### 多帧（FF + FC + CF）

UDS 载荷 > 7 字节时，需要分帧传输：

```
发送方（CCU）                        接收方（ECU）
  │                                     │
  │  FF: [10 xx xx 前5字节数据]  ────▶  │  首帧
  │                                     │
  │  ◀── FC: [30 00 01] ──────────────  │  流控（允许继续，STmin=1ms）
  │                                     │
  │  CF: [21 后7字节] ────────────────▶  │  连续帧 SN=1
  │  CF: [22 后7字节] ────────────────▶  │  连续帧 SN=2
  │  ...                                │
```

**FF 结构**：`[FF_PCI(1B) | FF_DL(2B, 12bit) | UDS前5字节]`

**FC 结构**：`[FC_PCI | FS | BS | STmin]`
- FS=0 允许继续，FS=1 等待，FS=2 溢出
- BS=0 无限制连续帧，STmin=1ms 最小间隔

**CF 结构**：`[CF_PCI | UDS后续数据]`，SN 从 1 递增到 15 后回绕到 0

## 6. 定时参数

| 参数 | 含义 | 默认值 |
|------|------|--------|
| N_As | 发送方发送 CAN 帧的超时 | 1000 ms |
| N_Ar | 接收方发送 FC 帧的超时 | 1000 ms |
| N_Bs | 发送方等待 FC 帧的超时 | 1000 ms |
| N_Cr | 接收方等待 CF 帧的超时 | 1000 ms |

外设应拒绝畸形的 ISO-TP 传输，并在不需重新上电的情况下恢复。

# 第三部分 UDS 诊断服务

## 7. 请求与响应格式

### 请求

```
[SID] [SubFunction] [Data...]
```

- SID：服务标识符（1 字节）
- SubFunction：子功能（可选，第 7 位 = 抑制肯定响应位）

### 肯定响应

```
[SID + 0x40] [SubFunction] [Data...]
```

### 否定响应

```
7F [SID] [NRC]
```

- 固定前缀 0x7F
- 原始 SID
- NRC：否定响应码

## 8. 常用 UDS 服务

### 0x10 — DiagnosticSessionControl（会话切换）

切换 ECU 诊断会话模式。

| 子功能 | 值 | 用途 |
|--------|-----|------|
| Default | 0x01 | 正常运行，只读诊断 |
| Programming | 0x02 | 固件更新，Flash 操作 |
| Extended | 0x03 | 受保护配置，扩展诊断 |

```
请求: 10 02              → 切到编程会话
响应: 50 02 00 32 01 F4  → 确认（ISO-TP SF 帧: 06 50 02 00 32 01 F4）
```

**P2 与 P2\***（组帧 can_protocol.c:905-912，常量 can_protocol.h:114-115）：
- **P2**（`00 32` = 50ms，`UDS_P2_TIMEOUT_MS`）：正常响应超时，MCU 必须在此时间内回复
- **P2\***（`01 F4` = 500×10ms = 5000ms，`UDS_P2_STAR_TIMEOUT_MS/10`）：发出 NRC 0x78（ResponsePending）后的扩展超时

### 0x11 — ECUReset（复位）

| 子功能 | 值 | 说明 |
|--------|-----|------|
| hardReset | 0x01 | 硬复位（最常用） |
| hardReset(suppress) | 0x81 | 硬复位，不发响应 |

```
请求: 11 01     → 硬复位
响应: 51 01     → 确认
```

### 0x22 — ReadDataByIdentifier（按标识符读数据）

```
请求: 22 [DID_H] [DID_L]
响应: 62 [DID_H] [DID_L] [Data...]
```

支持单次读取多个 DID（在一次请求中列出多个 DID）。

### 0x2E — WriteDataByIdentifier（按标识符写数据）

```
请求: 2E [DID_H] [DID_L] [Data...]
响应: 6E [DID_H] [DID_L]
```

逐 DID 门禁（can_protocol.c:1030-1070）：
- `0x2101` 充电使能 / `0x210D` 功率限值 → 需 Extended（`10 03`）+ 安全解锁；会话不满足回 NRC `0x22`，未解锁回 `0x33`
- `0x2010` 固件类型 / `0xF18C` SN / `0x2120` 公钥 / `0x2130` Qi IAP 控制 / `0x2131` Qi IAP 数据 → 需 Programming（`10 02`）+ 安全解锁
- 其余 DID 写 → NRC `0x31`（不可写，:1066-1069）

### 0x27 — SecurityAccess（安全访问）

详见[第 10 节](#10-安全访问)。

### 0x31 — RoutineControl（例程控制）

| 子功能 | 值 | 说明 |
|--------|-----|------|
| Start | 0x01 | 启动例程 |
| Stop | 0x02 | 停止例程 |
| RequestResults | 0x03 | 请求结果 |

```
请求: 31 01 FF 00  → 擦除非活跃槽（不携带地址/长度参数，APP 自动选槽）
响应: 71 01 FF 00  → 完成（长操作：先回 7F 31 78，完成后 ISO-TP SF 04 71 01 FF 00）
```

> 门禁（ota_download.c:280-313）：非 Programming → NRC `0x22`；未解锁 → `0x33`；len<4 → `0x13`；sub≠0x01 或 rid≠0xFF00 → `0x31`；擦除目标=运行槽对面槽；Device Info 保留区不擦。

### 0x34 — RequestDownload（请求下载）

```
请求: 34 [DataFormatID] [AddrAndLenFormatID] [MemAddr...] [MemSize...]
响应: 74 [LengthFormatID] [MaxNumberOfBlockLength...]
```

需 SecurityAccess Level 1。正响应中 `maxNumberOfBlockLength` 定义了后续 0x36 每包最大数据量。

### 0x36 — TransferData（传输数据）

```
请求: 36 [BlockSequenceCounter] [Data...]
响应: 76 [BlockSequenceCounter]
```

- BlockSequenceCounter 从 0x01 开始，每帧递增，到 0xFF 后回绕到 0x01
- 0x00 不作为正常序号使用

### 0x37 — RequestTransferExit（退出传输）

```
请求: 37
响应: 77
```

ECU 收到后执行校验（CRC32 + ECDSA 签名）。

### 0x3E — TesterPresent（测试仪在线）

保持非默认会话活跃，防止超时。

```
请求: 3E 00     → 有响应
响应: 7E 00

请求: 3E 80     → 抑制肯定响应（静默保活）
响应: 无
```

## 9. 会话管理

### 会话类型

| 会话 | 值 | 用途 | 安全状态 |
|------|-----|------|---------|
| Default | 0x01 | 正常运行，只读诊断 | 自动清除 |
| Programming | 0x02 | 固件更新，Flash 操作 | 需重新解锁 |
| Extended | 0x03 | 受保护配置，扩展诊断 | 需重新解锁 |

### 会话切换状态机

```
                    0x10 0x02
    ┌────────────┐ ──────────▶ ┌─────────────┐
    │   Default  │             │ Programming  │
    │   (0x01)   │ ◀────────── │   (0x02)     │
    └────────────┘  0x10 0x01  └─────────────┘
         ▲                         ▲
         │ 0x10 0x01               │ 0x10 0x02
         │ (或超时 5s)             │
    ┌────────────┐                 │
    │  Extended  │ ────────────────┘
    │   (0x03)   │   0x10 0x02（清除安全状态）
    └────────────┘
```

### 会话超时规则

- 非默认会话 5 秒内未收到 TesterPresent → 自动回退到 Default，清除安全解锁
- 从一个非默认切到另一个非默认 → 清除安全解锁状态
- 进入 Default → 中止固件传输，清除安全状态

### 何时需要重新验签

| 场景 | 是否需要重新走 27 01→03→02 |
|------|:--------------------------:|
| 同一编程会话内的多条指令 | ❌ 一次通过即可 |
| 从 Default 切到 Programming | ✅ |
| 从 Programming 切到 Default 再切回 | ✅ |
| S3 超时回退后重新进编程会话 | ✅ |
| 同一编程会话内读 DID | ❌ 只读操作不需要 |

### 各指令与安全权限

| 指令 | 是否需要验签 | 说明 |
|------|:----------:|------|
| `10 02` 编程会话 | ❌ | 前置条件，不需要验签 |
| `27 01/03/02` 验签 | — | 本身即验签操作，只做一次 |
| `22 21 33` 读 Qi 芯片版本 | ❌ | Qi IAP DID `0x2133` 只读（UART 0x01 上报），无需安全权限 |
| `2E 21 30 01` Qi IAP 启动升级（+大小） | ✅ | Qi IAP DID `0x2130` 写，需 Programming + 解锁（can_protocol.c:1051-1062） |
| `2E 21 31` Qi IAP 发数据 | ✅ | Qi IAP DID `0x2131` 写，同上门禁 |
| `22 21 32` 查 Qi IAP 状态 | ❌ | Qi IAP DID `0x2132` 只读，无需安全权限 |
| `2E 21 30 02` Qi IAP 中止 | ✅ | DID `0x2130` 写（data[3]=0x00/0x02 中止），同上门禁 |
| `31 01 FF00` 擦槽 | ✅ | 写操作，必须先验签 |
| `34` / `36` / `37` 下载 | ✅ | 写操作，必须先验签 |

## 10. 安全访问

### 挑战-响应流程（ECDSA P-256）

```
CCU (客户端)                        MCU (服务器)
    │                                    │
    │  27 01  ──────────────────────▶    │  请求种子
    │  ◀── 67 01 [seed 32B] ─────────   │  返回 32 字节随机种子
    │                                    │
    │  3. CCU 用私钥对 SHA256(seed) 签名  │
    │                                    │
    │  27 03 分片送 64B 签名 ────────▶    │  共 16 帧，每帧 4B
    │  27 02 触发验签 ──────────────▶    │
    │  ◀── 7F 27 78 (等待中) ────────   │  先收到 ResponsePending
    │  ◀── 67 02 (成功) ─────────────   │  数秒后出结果
```

**签名生成**（PC 侧）：

```python
import hashlib
seed = bytes([s0, s1, ..., s31])  # 从 27 01 响应取全部 32 字节
h = hashlib.sha256(seed).digest()
sig = ecdsa_sign(private_key, h)  # ECDSA P-256, 输出 64B R‖S
```

**签名分片发送**（27 03）：

```
帧1:  07 27 03 01 [sig0-3]   → 03 67 03 01
帧2:  07 27 03 02 [sig4-7]   → 03 67 03 02
...
帧16: 07 27 03 10 [sig60-63]  → 03 67 03 10
```

**安全要求**（can_protocol.c:1300-1490）：
- 种子每次 `27 01` 请求重新生成（LFSR + SysTick 时间熵，非硬件 RNG，`generate_random_seed` :603-613）
- **已解锁状态下 `27 01` 应答 `67 01` + 32×`0x00`**，不再发新种子（:1343-1352）
- 公钥存储在 Device Info 区（`0x0801D000+56`，boot_verify.c `DI_PUBKEY_OFFSET=56`），支持后期更换；Device Info 未配置时回落 Bootloader 内置公钥（`g_pubkey_magic=="KEYP"`）
- 连续 3 次验签失败锁定 30 秒（第 3 次失败当次即回 NRC `0x36`；`SECURITY_MAX_FAILURES=3` :71、`SECURITY_LOCKOUT_MS=30000` :70）
- 锁定期间 `27 01` 返回 NRC `0x37`（requiredTimeDelayNotExpired，:1333-1341）；锁定超时后下一次 `27 01` 清计数并正常发种子
- 切 Default Session **不**清失败计数（`session_reset_to_default` :560-568 不触碰 fail_count）
- `27 03` 分片序号错 → NRC `0x71`（接收缓冲清零，须从 blockSeq `0x01` 重发，:1404-1408）；种子未生成时发 `27 03`/`27 02`（验签失败后 `g_seed_generated` 已清）→ NRC `0x24`（:1429-1433）
- `27 02` 也可单帧直接携带 64B 签名（ISO-TP 多帧载荷 `27 02 <64B>`，len≥66 时跳过分片，:1437-1445）；标准流程仍是 `27 03`×16 + `27 02`
- 验签输入 = SHA256(seed 32B)（`sha256_hash(g_seed,32U)` :1451）+ `uECC_verify`（:1452），ECDSA P-256

## 11. 否定响应码 NRC

| NRC | 名称 | 常见场景 |
|-----|------|---------|
| 0x11 | ServiceNotSupported | APP 收到 `0x38` TransferSignature（签名在 XATO 头，由 `0x37` 验） |
| 0x12 | SubFunctionNotSupported | 非法 session / resetType |
| 0x13 | IncorrectMessageLength | 请求长度错误 |
| 0x14 | ResponseTooLong | 0x22 多 DID 读响应超 256B 缓冲（can_protocol.c:989-996） |
| 0x22 | ConditionsNotCorrect | 非 Programming 就擦/下载/写固件类型；非 Extended 写 `0x2101`/`0x210D`；充电故障态写 `0x2101=0x01`（can_protocol.c:1247-1251） |
| 0x24 | RequestSequenceError | 未擦就 0x34；未 0x34 就 0x36；SecurityAccess 序错（未 27 01 先发 27 03/27 02，或验签失败后裸发 27 02，:1429-1433） |
| 0x31 | RequestOutOfRange | 固件类型写值超出 0x01~0x03（can_protocol.c:1077-1084）；0x34 size 为 0 或超槽大小；DID 无效/不可写 |
| 0x33 | SecurityAccessDenied | 未解锁安全级别 |
| 0x35 | InvalidKey | ECDSA 验签失败 |
| 0x36 | ExceededNumberOfAttempts | 连续安全访问失败 3 次 |

## 13. 两个工程：Bootloader 与 APP

```
                CAN 250 kbps, ISO-TP, ID 0x18DA0D03 / 0x18DA030D
                ┌──────────────────────▲──────────────────────┐
                │                      │                      │
      ┌─────────┴──────────┐  ┌────────┴─────────┐
      │ Bootloader 16 KB   │  │ APP 48 KB/槽     │
      │ 0x08000000         │  │ 槽基址+256 入口  │
      │ 引导/验签/跳转     │  │ 充电业务 + UDS   │
      │ （无 UDS）         │  │ 擦写下载+Trial   │
      └─────────┬──────────┘  └────────┬─────────┘
                │   共享 metadata / XATO 头
                ▼
      0x0801C000 Primary  +  0x0801C800 Backup  +  0x0801D000 Device Info  +  0x0801E000 NVM
```

| 工程 | 目录 | 职责 |
|------|------|------|
| Bootloader | `qi_wireless_bootloader/` | 上电引导、槽选择、镜像校验、跳转（无完整 UDS；Safe Mode 应答 22 2113/3E 诊断帧 + 0x18FF260D 心跳，不执行下载，帧格式见 boot_safe_mode.c 头部注释） |
| APP | `qi_wireless_code_slotA/` | 充电业务、生命周期广播、全部 UDS 服务（含擦写下载）；Trial 确认 |

> 固件位置无关（运行时按 PC 判断所在槽，写入前自动重定位重签），只维护一份 APP 源码工程；`qi_wireless_code_slotB/` 副本已于 2026-09-17 删除。

**产线只烧 Bootloader + Slot A**。Slot B 出厂为空，第一次现场 OTA 写入。

### APP 与 Boot 的能力对比

架构反转后全部 UDS 服务在 APP 侧实现；常规 Boot 路径无 UDS（验签后直接跳转），仅 Boot Safe Mode 有最小诊断应答（见 §18）。

| 能力 | APP | Bootloader（常规路径 / Safe Mode） |
|------|-----|-----------|
| `0x10` 会话 | Default/Programming/Extended | 无 / 无（Safe Mode 也不响应 0x10） |
| `0x11` hardReset | 仅复位（metadata 已由 `0x37` 写 PENDING） | 无 / 无 |
| `0x27` SecurityAccess | ECDSA 解锁（32B seed + `27 03` 分块签名） | 无 / 无 |
| `0x22` 读 DID | 版本、槽、OTA 状态等 | 无 / 仅 `22 2113` 回 `62 21 13 FE <step>`，其余 22 DID 回 `7F 22 11`（boot_safe_mode.c:149-165） |
| `0x3E` TesterPresent | 非 suppress 回 `7E xx`；suppress/非 suppress 均刷新 S3（can_protocol.c:1509-1512/:1770） | 无 / 非 suppress 回 `02 7E xx`，suppress 不应答（boot_safe_mode.c:140-147） |
| `0x2E 2010` 写固件类型 | Programming + 解锁后可写 | 无 / 无 |
| `0x31 FF00` 擦槽 | 擦非活跃槽（APP 内完成） | 无 / 无（`0x34` 等无分支静默） |
| `0x34/0x36/0x37` | 完整下载路径（APP 内完成） | 无 / 无 |
| `0x38` TransferSignature | NRC 0x11（签名在 XATO 头，由 `0x37` 验） | 无 / 无 |
| Trial 确认/超时 | 100 ms 健康后确认 | 超限回滚 |

> 运行侧判定注意：旧版"发 `0x34` 区分 APP/Boot"的方法已失效；Boot Safe Mode 只对 `22 2113`/非 suppress `3E` 有应答、对 `0x34` 静默——须按约束 #1 的正证据组合判定，不得单凭某一服务有无应答下结论。

## 14. Flash 布局

| 区域 | 起始 | 大小 | 说明 |
|------|------|------|------|
| Bootloader | `0x08000000` | 16 KB | 引导 + Safe Mode |
| Slot A | `0x08004000` | 48 KB | 头 256B + 代码，入口 `0x08004100` |
| Slot B | `0x08010000` | 48 KB | 同上，入口 `0x08010100` |
| Metadata 主 | `0x0801C000` | 2 KB | `ota_metadata_t` 272B |
| Metadata 备 | `0x0801C800` | 2 KB | 先写备、再写主 |
| Device Info | `0x0801D000` | 4 KB | SN、ECDSA 公钥，OTA 擦写跳过 |
| NVM | `0x0801E000` | 8 KB | APP 配置 |

**Flash 擦除粒度**：AT32F426 的 Flash 页大小为 **1 KB（0x400）**。

### Metadata 结构（272B，magic `"MATO"`）

| 字段 | 含义 |
|------|------|
| `active_slot` | 最近一次已确认的槽（0=A，1=B） |
| `pending_slot` | 刚下完待试运行的槽；0xFE = 无 |
| `trial_state` | 0 IDLE / 1 PENDING / 2 ACTIVE / 3 CONFIRMED |
| `trial_slot` / `trial_retry_count` | 试运行槽与重试（默认上限 3） |
| `trial_timeout_sec` | APP 确认窗口，默认 10 秒 |
| `ota_state` | 0 IDLE / 1 DOWNLOADING（legacy，Boot 已忽略此字段） |
| `last_boot_reason` | 0x00 上电 / 0x01 软件复位 / 0x02 WDG / 0x03 OTA 激活 / 0x04 回滚 |

### Image Header（槽起始 256B，magic `"XATO"`）

```
槽基址 + 0x000  magic / image_length / crc32 / signature[64]
                / hdr_reserved_ver[16]（原 version 区，已废弃保留占位，打包固定填 0x00，fad6f77 起）
                / build_timestamp / reserved[160]
槽基址 + 0x100  应用镜像（向量表 + 代码），长度 ≤ 0xBF00
```

CRC32 和 ECDSA 只覆盖头后面的固件（不含头本身）。跳转地址 = 槽基址 + 256。

## 16. 生命周期广播

ECU 通过 CAN ID `0x18FF260D` 广播生命周期状态（周期发送已禁用：`lifecycle_is_periodic` 恒 0，lifecycle.c:80-84；原设计 1Hz `LIFECYCLE_PERIODIC_INTERVAL_MS=1000`，:38）：

```
Byte0: 状态码
Byte1: 0x41 = 'A'（APP 身份标记，lifecycle.c:70）
Byte2~7: 扩展信息
```

> Boot Safe Mode ABT 心跳帧 `01 41 42 54 cause step A5 00`：Byte1 同为 `0x41`，'B'（`0x42`）位于 Byte2（boot_safe_mode.c:79-92）；下表状态码描述 APP 事件帧。

| 状态码 | 名称 | 含义 |
|--------|------|------|
| 0x01 | BOOTUP | 事件驱动：首次 SIT1145 唤醒后由 `can_protocol_poll` 触发发送（非上电即时）；bus-off 恢复也会补发（lifecycle.c:95-105/:120-127） |
| 0x02 | INITIALIZING | 正在初始化 |
| 0x03 | OPERATIONAL | 已就绪 |
| 0x04 | DEGRADED | 降级运行 |
| 0x05 | FAULT | 严重故障 |
| 0x06 | SHUTDOWN | 准备断电 |

# 第五部分 OTA 升级流程

## 17. 端到端 OTA 全景

### 场景 A — 板子正在跑 APP（现场升级，唯一路径）

```
主机                        APP                        Bootloader
 │  10 02                    │                             │
 ├─────────────────────────▶│ 50 02                       │
 │  27 01/03/02 解锁         │                             │
 ├─────────────────────────▶│ 67 02                       │
 │  31 01 FF00 擦非活跃槽    │                             │
 ├─────────────────────────▶│ 71 01 FF00                  │
 │  34 / 36×N / 37 下载验签  │                             │
 ├─────────────────────────▶│ 37 验签通过 → 写 trial PENDING│
 │  11 01                    │ 仅复位（不写 metadata）      │
 ├─────────────────────────▶│ 51 01 → reset ─────────────▶│
 │                           │                             │ select_boot_slot → 验签
 │                           │◀──── 跳 trial 槽入口 ───────┤
 │  22 F195 读版本           │ 100ms 后 CONFIRMED           │
```

### 场景 B — 空片 / 双槽无效（Boot 挂起）

Boot 无完整 UDS，Safe Mode 在 `while(1)` 内仅应答 22 2113/3E 诊断帧并在
`0x18FF260D` 发心跳，**不执行下载、不能通过 CAN 救砖**。
唯一恢复手段：产线 `merge_prod_bin.py` 合并镜像从 `0x08000000` 整片烧录。

### 两种场景的差别

| | 场景 A（APP 内下载） | 场景 B（Boot 挂起） |
|--|--|--|
| 触发方式 | APP 内 `10 02`+`27` 解锁+`31/34/36/37`，`0x37` 验签后写 trial PENDING，`11 01` 仅复位 | 无 UDS 可用 |
| 镜像链接要求 | 链接到 Slot A（`0x08004100`）；写 B 槽时 OTA 脚本自动重定位重签 | 同左 |
| 恢复手段 | 正常 OTA 流程 | 产线整片烧录 |

## 18. Bootloader 工作流

入口：`qi_wireless_bootloader/mdk_user/Src/main.c`

```
上电 / 复位
  │
  ├─ system_clock_config()  180 MHz
  ├─ boot_metadata_init(&g_meta)  主区 → 备份 → 默认值
  ├─ last_boot_reason = detect_boot_reason()
  │   （ota_state=DOWNLOADING 已忽略，legacy metadata）
  │
  ├─ process_trial_state(&g_meta)
  ├─ select_boot_slot()
  ├─ try_boot_slot(选中槽)  只验签，通过后 jump
  │     失败 → try_boot_slot(另一槽)
  └─ 双槽失败 → enter_safe_mode()
```

### enter_safe_mode

- 挂起 + 最小 CAN 诊断应答（HEAD `boot_safe_mode.c`，17bc8ab 起行为固化）：主循环应答 `22 2113`（`62 21 13 FE <fail_step>`，现行 ISO-TP SF `05 62 21 13 FE <fail_step> CC CC`）与非 suppress 的 `3E`；其余 `22` DID 回 `7F 22 11`；`0x34` 等无分支静默；每 500ms 在 `0x18FF260D` 发 ABT 心跳 `01 41 42 54 cause fail_step A5 00` 并重切 SIT1145 Normal。无下载服务、不能通过 CAN 救砖
- 空片 / 双槽无效时进入，唯一恢复手段是产线 `merge_prod_bin.py` 整片烧录

### 下载目标槽选择（APP `ota_download.c::inactive_slot`）

擦写目标恒为**当前运行槽（VTOR 判定）的对面槽**，不查 metadata valid 标志，不覆盖正在跑的镜像（ota_download.c:38-40，erase 入口 :313）：

| 运行槽（VTOR） | 擦写目标 |
|------|---------|
| Slot A（`0x08004000`） | Slot B |
| Slot B（`0x08010000`） | Slot A |

> 旧 Boot 侧 `select_inactive_slot`（按 active_slot/valid 标志选槽）已随架构反转移除，仓库内无此函数；出厂空片/双槽无效场景不走 OTA 选择逻辑，由 Boot Safe Mode + 产线整片烧录处理（§17 场景 B）。

### boot_verify_image（镜像校验 6 步）

| 步骤 | 校验内容 |
|------|---------|
| 1 | magic == XATO |
| 2 | 0 < image_length ≤ 槽大小 − 256 |
| 3 | CRC32(固件) == header.crc32 |
| 4 | Reset Handler（清 Thumb 位）落在 [入口, 槽末) |
| 5 | 公钥完整性（`g_pubkey_magic == "KEYP"`） |
| 6 | SHA256(固件) + uECC_verify(公钥, signature) |

### boot_jump_to_app

关中断 → 复位 CAN1（+关时钟）→ 关 SPI1（+关时钟，收发器接口断电；跳转路径**无**显式 SIT1145 Standby 命令）→ 关 SysTick → 清 NVIC → CONTROL=0 → VTOR = app_addr → 读 MSP / Reset_Handler → 内联汇编 `msr msp; bx` 跳转（boot_jump.c:75-135）

## 19. APP 工作流

入口：`qi_wireless_code_slotA/mdk_user/Src/main.c`

```
SCB->VTOR = 运行地址实测（PC ≥ 0x08010000 → 0x08010100，否则 0x08004100；main.c:44-55）
system_clock_config / NVIC GROUP_4
timer_drv_init / board_gpio_init / nvm_drv_init
can_driver_init  (SIT1145 初始化；当前 CAN_LP_STANDBY_ENABLE=0，上电不进 Standby)
can_protocol_init  (当前编译开关下 trial/非 trial 均 g_lp_need_online=1，首次 poll 统一 enter_normal，CAN 常在线；can_protocol.h:63 + can_protocol_init)
qi_uart_init
__enable_irq()
lifecycle_init  (注册 bus-off 回调；BOOTUP 在首次 CAN 唤醒后事件驱动发送，非上电即时)
ota_trial_init  (若本镜像正在 trial，启动 10s 窗口)

while (1)
  timer_poll / can_protocol_poll / can_driver_poll / qi_uart_poll
  lifecycle_poll / board_charge_poll
  ota_trial_poll  (健康 100ms 后 CONFIRMED；超时 NVIC_SystemReset)
```

### OTA 下载与复位切槽（唯一路径）

```
主机 → APP : 10 02          Programming Session
主机 → APP : 27 解锁 → 31 01 FF00 擦非活跃槽 → 34/36 下载 → 37 验签
APP: 0x37 验签通过 → commit_trial() 写 metadata trial PENDING
主机 → APP : 11 01          仅复位（不写 metadata）
    → SHUTDOWN 广播 + 等 TX
    → NVIC_SystemReset
Bootloader: select_boot_slot → try_boot_slot 验签 → 跳新槽 Trial
```

- `11 01` 处理：发正响应 → SHUTDOWN 广播 → 等 TX 空闲 → `NVIC_SystemReset`；metadata 已由 `0x37` 写为 trial PENDING
- 空片 / 双槽无效：Boot 挂起（无 UDS），靠产线 `merge_prod_bin.py` 从 `0x08000000` 救砖

### Trial 确认

`ota_trial_init`：仅当 `trial_state==ACTIVE` 且 `trial_slot == ota_running_slot()`（VTOR 判断）才打开窗口。

`ota_trial_poll`：
- 超过 `trial_timeout_sec`（10s）→ `NVIC_SystemReset()`，Bootloader 看到仍是 ACTIVE，累加 retry，超限回滚
- 启动满 100ms 后 `ota_confirm_trial()`：`active_slot = trial_slot`，`trial_state = CONFIRMED`

## 20. OTA 逐步 CAN 帧

适用：APP 运行中执行 UDS 下载（下载在 APP 内完成；Boot 无完整 UDS，Safe Mode 仅应答 22 2113/3E 诊断帧 + 心跳，不执行下载）。

请求 ID `0x18DA0D03`，响应 ID `0x18DA030D`，扩展帧，250 kbps。

### 必做顺序

```
10 02 进编程会话
  → 27 01 要 seed
  → 27 03 分片送 64B 签名（16帧）
  → 27 02 验签（可能先 7F 27 78）
  → 2E 2010 01 选 APP 固件类型
  → 31 01 FF00 擦非活跃槽        ← 不擦直接 34 会 NRC 0x24
  → 34 申请下载
  → 36 按块写镜像（必须是 pack_image.py 打的包）
  → 37 结束传输并验签
  → 11 01 复位进试用
```

### 逐步 CAN 数据

| 步 | 作用 | 发出 (8字节) | 期望响应 |
|----|------|-------------|---------|
| 1 | Programming Session | `02 10 02 00 00 00 00 00` | `06 50 02 00 32 01 F4`（P2=50ms, P2*=5000ms） |
| 2 | RequestSeed | `02 27 01 00 00 00 00 00` | ISO-TP 多帧：`67 01` + 32B seed（载荷 34B；已解锁时 32×`0x00`） |
| 3 | 签名分片 ×16 | `07 27 03 ss d0 d1 d2 d3` | `03 67 03 ss ...` |
| 4 | SendKey 验签 | `02 27 02 00 00 00 00 00` | 先 `7F 27 78`，再 `02 67 02` |
| 5 | 固件类型 APP | `04 2E 20 10 01 00 00 00` | `03 6E 20 10 ...` |
| 6 | 擦非活跃槽 | `04 31 01 FF 00 00 00 00` | 先 `7F 31 78`，再 `04 71 01 FF 00` |
| 7 | RequestDownload | 见下文 | `04 74 20 01 00` (maxBlock=256) |
| 8 | TransferData | `36` + blockSeq + 数据 | `02 76 ss ...` |
| 9 | TransferExit | `01 37 00 00 00 00 00 00` | 先 `7F 37 78`，再 `01 77` |
| 10 | 复位 | `02 11 01 00 00 00 00 00` | `02 51 01`，MCU 复位 |

**注意**：第 6 步擦槽只擦固件 Slot 区域，不擦 Device Info 保留区（`0x0801D000`~`0x0801DFFF`），SN 等设备信息 OTA 后仍保留。

### 0x34 RequestDownload 示例

格式要求（ota_download.c:386-446）：ALFID 的 addr_n/size_n 必须各为 1~4，`alfid=0x00` 回 NRC `0x13`（不存在"无地址/长度"的简单写法）；mem_size 为 0 或超槽大小回 `0x31`；地址值被忽略（目标槽已由 `31 01 FF00` 擦除步骤锁定）。

正式版（size = 打包文件总长，含 256B 头）：

```
UDS: 34 00 44 00 00 00 00 00 00 10 00
     SID ALFID  4B 地址(忽略)   4B 长度

FF:  10 0B 34 00 44 00 00 00    (ISO-TP 首帧)
CF:  21 00 00 00 10 00 00 00    (ISO-TP 连续帧)
```

成功响应：`74 20 01 00`（ALFID=0x20，maxNumberOfBlockLength=0x0100=256，即 `OTA_DL_MAX_BLOCK_LEN`）

### 0x36 TransferData

blockSeq 从 0x01 起，FF 下一帧是 0x01（跳过 0x00）。

单帧最多塞 5 字节数据：

```
07 36 01 d0 d1 d2 d3 d4
```

完整刷写走 ISO-TP 多帧，每包最多 254 字节数据。

### S3 超时保活

擦 Flash / 多帧传输过程中，每 5 秒要发一次 TesterPresent 防止掉回 Default Session（`SESSION_TIMEOUT_MS=5000`，can_protocol.h:167）。`3E 00` 与 `3E 80`（suppress）均刷新 S3 计时，且**任意诊断请求**都会刷新（uds_process_message :1770；handle_tester_present :1509-1512）。长步骤会先回 `7F xx 78`（ResponsePending），超时放到 8~10 秒。

## 21. Trial 试运行与回滚

### Trial 状态机

| 进入 | 动作 |
|------|------|
| IDLE | 无 |
| PENDING | → ACTIVE，retry++，last_boot_reason=OTA_ACT，保存 |
| ACTIVE | 未确认又回到 Boot → retry++；> max_retries → 回滚 |
| CONFIRMED | → IDLE，清 retry |

**回滚动作**：IDLE、pending_slot=none、切 active_slot 到另一 valid 槽、BOOT_REASON_ROLLBACK

**回滚原则**：
- 未通过 boot_verify_image 6 项校验（magic/长度/CRC32/Reset Handler 落槽/公钥 `KEYP`/ECDSA）的镜像不会被跳转（boot_verify.c fail_step 1-6）
- Trial 未确认不会改写 active_slot
- 双槽无效永远能进 Safe Mode

## 22. 错误与回滚速查

| 现象 | 处理 |
|------|------|
| `7F 34 22` | APP 在但不在编程会话（现固件 0x34 无 0x11 分支）：先 `10 02` + `27` 解锁；Boot safe mode 对 0x34 静默不应答（约束 #1） |
| `7F 34 24` | 没擦就 34 |
| `7F xx 33` | 没过 0x27 |
| `7F xx 22` | 不是 Programming Session，或 S3 掉线 |
| `7F 36 73` | blockSeq 错，需重新 34 |
| `7F 37 72` | 长度/CRC/槽内 Reset/ECDSA 失败 |
| 新 APP 10s 内无确认 | APP 自己复位；retry 超限切回上一 valid 槽 |
| 双槽都验不过 | Safe Mode，可再刷 |

## 24. 中断与时基

Bootloader 与 APP 各有一份 `at32f422_426_int.c`，结构相同。优先级分组 4 位抢占。

| 中断 | 优先级 | 处理 |
|------|--------|------|
| SysTick | 内核 | `timer_tick_inc()`，1ms |
| CAN1 RX | (1,0) | 硬件缓冲 → 软件 FIFO，协议在主循环 |
| CAN1 ERR | (2,0) | 总线关闭恢复 |
| USART2 | (3,0) | 仅 APP：Qi RX FIFO |
| Fault | — | 写标记到 0x20000000 后 `NVIC_SystemReset()`（HardFault/MemManage/BusFault/UsageFault 同构，at32f422_426_int.c:55-95） |

软件定时器最多 16 个。APP 生命周期用 `timer_get_tick()` 自己数 1000ms，不是独立硬件定时器。

## 25. 实现约束

1. **下载在 APP 内完成**（`31/34/36/37`，见场景 A；Boot 无完整 UDS）。运行侧判定只按正证据，不得按 NRC 值分叉（旧"`0x34` 回 `7F xx 11` → APP"判据与现固件相反：APP 默认会话对 `0x34` 回 NRC `0x22`，路径无 `0x11` 分支）：对 `0x34` 的任何应答（正响应或任意 NRC）= APP；`22 2113` 应答且 `62 21 13` 后字节为 `0xFE` = Boot safe mode（APP 的 DID `0x2113`=active slot 也正响应，slot 字节 `0x00/0x01` 永不 `0xFE`）；无应答 ≠ 不在 APP，先 Standby 唤醒收敛（`3E 80` burst）+ 释放 UDS 通道监听 `0x18FF260D` 生命周期帧（AWK `01 41 57 4B`/BOOTUP `01 41 00`=APP 启动，ABT `01 41 42 54`=Boot safe mode）再判；全静默=UNKNOWN，退出并取证。实现：`python_tools/2.functional test script/zcanpro_charge_start.py probe_location`
2. **镜像必须带 XATO 头**，且 Reset Handler 落在将要写入的槽（boot_verify.c check 3b 按目标槽地址校验）。OTA 到 B 不再需要 B 链接工程：A 链接镜像由 OTA 脚本自动重定位+重签后写入（`zcanpro_ext_ota_auto.py relocate_image_to_slot`）
3. **私钥与 Bootloader 公钥绑定。** 路径 `docs/keys/private.pem`。换密钥后重烧 Bootloader
4. **0x38 可选。** 打包时头里已签名则不必发 0x38
5. **不实现看门狗。** Trial 失败靠 APP 10s 后 `NVIC_SystemReset`
6. **metadata 掉电安全：** 先 Backup 再 Primary。APP 触发时不把运行槽标无效
7. **S3 = 5s**（`SESSION_TIMEOUT_MS`，can_protocol.h:167）。擦写/多帧传输过程中要插 TesterPresent（`3E 00` 或 `3E 80` 均续期）。宿主脚本现行防护：锁定等待/长间隙每 3s 发 `3E 80` keepalive（3s<5s 留 2s 余量），写步撞 NRC 0x22/0x33 兑底=重发会话+完整重解锁+重试一次（`zcanpro_charge_start.py` `S3_KEEPALIVE_INTERVAL_S=3.0`/`_wdbi_with_s3_guard`）
